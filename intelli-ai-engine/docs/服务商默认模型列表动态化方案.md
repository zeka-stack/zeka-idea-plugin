# 服务商默认模型列表动态化方案

## 1. 问题

`AIProviderType` 枚举里写死了 `defaultModel` + `supportedModels`。模型迭代快，每次改列表都要发版，且与「用户点刷新从厂商 `/models` 拉全量」是两件不同的事。

## 2. 现状

### 2.1 插件侧三层

```text
UI 下拉框数据源优先级（打开设置时）
  1) 本地缓存（上次「刷新模型」成功写入的文件）
  2) AIProviderType.getSupportedModels()  ← 写死在代码里（痛点）
  3) 用户点「刷新模型」→ provider.getAvailableModels() → 厂商 /models → 写回缓存

特例：ZhipudModelListProvider
  → SiteContents.MODEL_API_BASE_URL + "/zhipu"
  → 失败再回退固定列表
```

### 2.2 远程维护位置（已核实）

仓库：`supports/zeka-stack-api/`

| 项 | 现状 |
|----|------|
| Controller | `ModelController` → `@RestControllerWrapper("/plugin/v1/models")` |
| 现有接口 | `GET /api/plugin/v1/models/zhipu` |
| 数据来源 | `application.yml` → `zhipu.default-models`（`ZhipuModelService` 读取） |
| 响应包装 | 统一 `R`：`{ success, code, message, data: { provider, models, total } }` |
| 文档 | `model-api.md` / `CLAUDE.md` 已规划扩展多服务商 |

线上探测（2026-08-06）：

```text
✅ GET https://zekastack.dong4j.site/api/plugin/v1/models/zhipu
   → success=true，返回 yml 中的 glm 列表

❌ GET https://zekastack.dong4j.site/api/plugin/model/zhipu
   → success=false code=4101（插件 SiteContents.MODEL_API_BASE_URL 当前指向这里）
```

**结论：远程 catalog 基础设施已有，但插件 URL 写错（少了 `v1/models`），智谱远程拉取实际一直失败并回退本地 seed。**

需要区分两个概念：

| 概念 | 用途 | 更新频率期望 |
|------|------|----------------|
| **推荐/默认目录（catalog）** | 首次展示、无 Key、离线、默认模型 | 希望**不发版**也能改（改 API yml / 配置即可） |
| **厂商实时列表（live）** | 用户点刷新拿到账号可见模型 | 已有，依赖厂商 API |

本方案只解决 **catalog**，live 刷新路径保留。

---

## 3. 方案选项

### 选项 A（最小）：枚举只留 1 个 seed + 依赖刷新

- 改动极小；首次/无 Key/刷新失败体验差；默认模型仍要发版

### 选项 B（推荐）：扩展 zeka-stack-api + 插件对接远程 Catalog

在已有 `GET /api/plugin/v1/models/{provider}` 上扩展，而不是另起 `/catalog` 新体系。

**API 侧（zeka-stack-api）：**

1. 将 `zhipu.*` 配置泛化为多服务商，例如：

```yaml
plugin:
  models:
    providers:
      glm:
        default-model: glm-4.7
        models:
          - glm-4.7
          - glm-4.6
      zhipu:  # 别名 → 同 glm
        alias-of: glm
      deepseek:
        default-model: deepseek-v4-flash
        models:
          - deepseek-v4-pro
          - deepseek-v4-flash
      anthropic:
        default-model: claude-sonnet-4-20250514
        models: [...]
```

2. `GET /api/plugin/v1/models/{providerId}`：按 provider 返回 `{ provider, defaultModel, models, total }`
3. 可选：`GET /api/plugin/v1/models` 一次返回全量（减少设置页切换时的请求）
4. 保持现有 `R` 包装；`/zhipu` 兼容不删
5. 首期仍用 **yml 静态列表**（与现在 zhipu 一样），不爬厂商；后续再按需接厂商 `/models` 代理

**插件侧（intelli-ai-engine）：**

1. 修正 `SiteContents.MODEL_API_BASE_URL` → `https://zekastack.dong4j.site/api/plugin/v1/models`
2. 新增 `ModelCatalogService`：按 `providerId` 拉远程 → 本地 TTL 缓存 → seed 兜底
3. 枚举瘦身：只留极简 seed（1～2 个）+ 元数据
4. 下拉框优先级：

```text
live 缓存（刷新模型） → 远程 catalog 本地缓存 → AIProviderType seed
```

5. 泛化/退役 `ZhipudModelListProvider` 硬编码 `/zhipu`

| 项 | 评估 |
|----|------|
| 工作量 | 中（API 多 provider 配置 + 插件 CatalogService + 修 URL） |
| 风险 | 低：远程失败回退 seed；与现网 zhipu 接口同形 |
| 收益 | **改 yml 部署 API 即可更新推荐列表，插件不用发版** |

### 选项 C：仅 jar 内 `resources/models/catalog.json`

- 比枚举好维护，但仍要发版；可作 B 的打包兜底，不单独作为终态

---

## 4. 推荐：选项 B

### 4.1 providerId 对齐（需约定）

插件 `AIProviderType.providerId` 与 API path 必须一致，例如：

| 插件 providerId | API path |
|-----------------|----------|
| `glm` | `/glm`（智谱；保留 `/zhipu` 别名 → 同数据） |
| `deepseek` / `deepseek_anthropic` | 分 key 或共享列表 + 各自 defaultModel |
| `anthropic` | `/anthropic` |
| `moonshot` / `moonshot_anthropic` | 同上 |
| `doubao` / `doubao_anthropic` | 同上 |

**推荐：OpenAI 口与 Anthropic 口分 key**；列表可在 yml 里用 YAML anchor 复用。

### 4.2 攻击面

| 角度 | 结论 |
|------|------|
| 依赖失效 | 远程挂了 → 本地 catalog 缓存 → seed |
| 规模 | 每厂商几～几十条，无压力 |
| 回滚 | API 回滚 yml 即可 |
| 前提崩塌 | 无：zeka-stack-api 已存在且 zhipu 已通 |

### 4.3 明确不做（首期）

- 爬取各厂商官网自动生成
- 用 catalog 替代「刷新模型」live `/models`
- 强制覆盖用户已选模型
- Custom 模型名启发式

### 4.4 交付切分

| 阶段 | 内容 |
|------|------|
| B0 | **修插件 URL**（立刻让智谱远程生效）+ 文档对齐 |
| B1 | API：多服务商 yml + `/{providerId}` + 可选全量接口；响应增加 `defaultModel` |
| B2 | 插件：`ModelCatalogService` + 下拉优先级（**已落地**）；枚举瘦身可后续 |
| B3 | 主服务商 catalog 填全（API yml 已初填，**待部署** zeka-stack-api） |

### 4.5 确认与进度

1. ✅ 选项 B，B0→B3
2. ✅ providerId 以插件为准，`zhipu` → `glm` 别名
3. ✅ 下拉：**live 缓存 > catalog > seed**
4. ✅ Anthropic live `/v1/models` + catalog 兜底

进度：B0 / Anthropic 分页 / API B1 代码 / 插件 B2 已完成；需部署 API 后全量 catalog 才线上可用。

### 4.6 Anthropic 类 live 模型列表（补充确认）

官方 Anthropic Models API：

```text
GET {base}/v1/models
Header:
  x-api-key: <key>
  anthropic-version: 2023-06-01
  （兼容网关同时带 Authorization: Bearer <key>）

Response:
{
  "data": [ { "id": "claude-sonnet-4-20250514", "type": "model", ... }, ... ],
  "has_more": true,
  "first_id": "...",
  "last_id": "..."
}
分页：?after_id=<last_id>&limit=100
```

插件现状：`AnthropicLikeProvider.getAvailableModels()` **已实现**该接口，且所有 `*_ANTHROPIC` 工厂入口均走该类（或子类）。

线上探测（无有效 Key）：

| Base | `/v1/models` | 说明 |
|------|--------------|------|
| `api.anthropic.com` | 401（需 Key） | 官方支持 |
| `api.deepseek.com/anthropic` | 401 | 端点存在 |
| `open.bigmodel.cn/api/anthropic` | 有响应 | 端点存在 |
| `ark.../api/coding` | 401 | 端点存在 |
| `api.moonshot.cn/anthropic` | **404** | Anthropic 口可能不提供 models |
| `api.hunyuan.../anthropic` | **404** | 同上 |

**落地要求（与 catalog 并行）：**

1. 保留/强化 Anthropic `GET /v1/models`（含 `has_more` 分页）
2. 厂商 Anthropic 口 404 时：回退 **catalog**（zeka-stack-api）→ seed，不假装成功
3. Catalog 为每个 `*_anthropic` providerId 维护推荐列表（与 OpenAI 口可 YAML anchor 复用）
4. 不强制所有厂商 Anthropic 口都实现 live `/models`（能力以探测为准）
