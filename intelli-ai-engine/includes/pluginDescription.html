IntelliAI Engine

⚡ Unified AI Infrastructure for IntelliJ Plugins: The foundation layer that powers all IntelliAI plugins, providing seamless, unified, and high-performance AI capabilities

GitHub | Issues | Homepage

Think of IntelliAI Engine as the "power behind the throne" - a quiet, invisible engine that makes all AI-powered plugins work together seamlessly. It doesn't provide features itself, but it powers Javadoc generation, Changelog writing, Terminal command generation, and more.

Why We Built This?

Building AI-powered plugins is hard. Every plugin needs to integrate with OpenAI, Claude, local models, handle API keys, manage streaming responses, track tokens, and build UI. This leads to duplicated code, inconsistent behavior, and maintenance nightmares.

We asked ourselves: What if we could build this once and reuse it everywhere?

IntelliAI Engine is the answer. It's the shared foundation that lets every plugin focus on doing one thing well, while Engine handles all the messy AI infrastructure details.

What Engine Does For You

  • 🤖 One Setup for All Plugins: Configure AI providers once (OpenAI, Claude, Qwen, Ollama, etc.), and every IntelliAI plugin can use them instantly
  • 🔒 Secure Key Management: Your API keys are stored securely using IntelliJ's Password Safe, with automatic service naming to prevent conflicts
  • ⚙️ Smart Configuration: Unified settings panel for credentials, models, rate limits, with instant validation so you know everything works
  • 📊 Usage Tracking: Automatic token counting and usage statistics across all your AI-powered plugins
  • 🎨 Ready-to-Use Components: Inline generation buttons, status bar entries, progress dialogs - all pre-built for plugins to use
  • 🛡 Reliable Error Handling: Consistent error recovery, retry logic, and logging across all plugins

The Philosophy: Separation of Concerns

Engine follows a simple design principle:

[ Engine Layer ]   - Stable, reusable AI infrastructure
       ↑
[ Plugin Layer ]    - Focused on specific problems
       ↑
[ User Experience ] - You just click, it just works

This means:

  • Plugins stay focused: Each plugin does one thing well (Javadoc, Changelog, Terminal, etc.) without worrying about AI details
  • Consistent behavior: All plugins share the same error handling, logging, and UX patterns
  • Better experience for you: Configure once, use everywhere. No need to enter the same API keys in five different places

Why Plugins, Not One Big Plugin?

You might ask: Why not put all features into one "All-in-One" plugin?

We considered this approach carefully, but chose plugin-based architecture for these reasons:

  • 🎯 You Choose What You Need: Not everyone needs Javadoc, Changelog, Terminal, and Tracer at the same time. With plugins, you install only what you use, keeping your IDE lightweight and fast
  • ⚡ Faster Updates & Iterations: Each plugin can evolve independently. We can fix Terminal bugs without waiting for Javadoc release, or add new Swagger features without touching Engine. Updates are smaller, faster, and less risky
  • 🧹 Smaller Attack Surface: If you don't use Changelog, you don't install it. This means less code running in your IDE, fewer permissions requested, and reduced security risk
  • 🛡 Failure Isolation: If one plugin crashes, others keep working. A bug in Terminal won't break Javadoc generation
  • 📊 Easier to Understand & Discover: Clear plugin names make features discoverable. You can search "AI Terminal" and find it immediately, rather than digging through settings of a monolithic plugin
  • 🔄 Flexible Dependency: Some plugins require additional dependencies (e.g., Checkstyle-IDEA for Repairer). Plugin-based approach lets users avoid installing unnecessary dependencies
  • 🏗 Better for Open Source: Different contributors can work on different plugins. Community can improve Javadoc while someone else enhances Terminal, without merge conflicts

In short: Plugins give you choice, flexibility, and control. Engine gives them unified AI infrastructure. It's the best of both worlds - powerful capabilities without bloat.

为什么要构建这个？

构建 AI 驱动的插件很难。每个插件都需要集成 OpenAI、Claude、本地模型，处理 API Key、管理流式响应、统计 Token、构建 UI。这导致代码重复、行为不一致和维护噩梦。

我们问自己：如果我们能构建一次并在任何地方复用，会怎样？

IntelliAI Engine 就是答案。它是共享的基础设施，让每个插件专注于做好一件事，而 Engine 处理所有繁琐的 AI 基础设施细节。

Engine 为你做什么

  • 🤖 一次配置，全部通用：配置一次 AI 服务商（OpenAI、Claude、通义千问、Ollama 等），所有 IntelliAI 插件立即可用
  • 🔒 安全的密钥管理：使用 IntelliJ Password Safe 安全存储 API Key，自动生成服务名避免冲突
  • ⚙️ 智能配置：统一设置面板管理凭证、模型、速率限制，即时验证，让你知道一切正常工作
  • 📊 使用量追踪：自动统计所有 AI 插件的 Token 数量和使用情况
  • 🎨 即用型组件：内置生成按钮、状态栏入口、进度对话框，插件直接使用
  • 🛡 可靠的错误处理：所有插件共享一致的错误恢复、重试逻辑和日志记录

设计理念：职责分离

Engine 遵循一个简单的设计原则：

[ 引擎层 ]   - 稳定、可复用的 AI 基础设施
       ↑
[ 插件层 ]    - 专注于解决特定问题
       ↑
[ 用户体验 ] - 你只需点击，它就工作

这意味着：

  • 插件保持专注：每个插件专注于做好一件事（Javadoc、Changelog、Terminal 等），无需关心 AI 细节
  • 一致的行为：所有插件共享相同的错误处理、日志和 UX 模式
  • 更好的体验：一次配置，到处使用。无需在五个不同地方输入相同的 API Key

为什么选择插件化，而不是一个大全插件？

你可能会问：为什么不把所有功能放到一个"全能"插件里？

我们仔细考虑了这个方案，但最终选择插件化架构，原因如下：

  • 🎯 你选择你需要的功能：不是每个人同时需要 Javadoc、Changelog、Terminal 和 Tracer。通过插件化，你只安装需要的，保持 IDE 轻量级和快速
  • ⚡ 更快的更新和迭代：每个插件可以独立演进。我们可以修复 Terminal 的 bug 而不需要等 Javadoc 发布，或者添加新的 Swagger 功能而不影响 Engine。更新更小、更快、风险更低
  • 🧹 更小的攻击面：如果你不使用 Changelog，就不安装它。这意味着在你的 IDE 中运行的代码更少，请求的权限更少，降低安全风险
  • 🛡 故障隔离：如果一个插件崩溃，其他插件继续工作。Terminal 的 bug 不会导致 Javadoc 生成失效
  • 📊 更容易理解和发现：清晰的插件名称让功能更容易发现。你可以搜索"AI Terminal"并立即找到，而不是在一个单一插件 的设置中翻找
  • 🔄 灵活的依赖：某些插件需要额外依赖（例如 Repairer 需要 Checkstyle-IDEA）。插件化方式让用户可以避免安装不必要的依赖
  • 🏗 对开源更友好：不同的贡献者可以专注于不同的插件。社区可以改进 Javadoc，同时有人增强 Terminal，而不会有合并冲突

简而言之：插件给你选择、灵活性和控制。Engine 给它们统一的 AI 基础设施。这是两全其美——强大的能力，没有臃肿。
