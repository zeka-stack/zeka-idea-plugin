下面我只聚焦「如何提高文本匹配度」，不引入任何你不需要的架构 / IDEA 重功能，而且全部都是 Editor 层可落地优化。

⸻

一、先定一个核心原则（非常重要）

文本匹配 ≠ 字符串相等
而是：相同修改意图 + 不同表面形式

你要做的是：
👉 判断「这个地方，如果用户看到，也大概率会想“我也要改一下”」

⸻

二、分 4 层逐步增强匹配度（推荐顺序）

每一层都 可单独上线，不会推翻 MVP

⸻

① 规范化（Normalization）——命中率提升最大 ⭐⭐⭐

这是性价比最高的一步，而且完全不需要 AI。

1️⃣ 对 before / after 做统一规范化

String normalize(String s) {
return s
.toLowerCase()
.replaceAll("_+", "_")
.replaceAll("\\s+", "")
.replaceAll("[^a-z0-9_]", "");
}

例子：

原始 normalize 后
User_Name username
user-name username
userName username

👉 比较用 normalize，替换用原文

⸻

2️⃣ 基于 normalize 计算“修改模式”

before: user_name
after:  username

pattern:

- remove underscore
- lowercase

你不用真的建规则树，只要能稳定复用就行。

⸻

② Token 化匹配（避免误伤）⭐⭐⭐

纯字符串查找的问题是：误命中非常多。

推荐做法：按“词”拆，而不是整段

示例拆分规则（简单版）

List<String> tokens(String s) {
return Splitter.onPattern("[^A-Za-z0-9]+")
.omitEmptyStrings()
.splitToList(s);
}

然后：
• oldText 的 token 集
• 候选文本的 token 集
• 交集比例 ≥ 阈值 才认为“相似”

old:   user_name
other: user_name_list

token overlap = 1 / 2 → ✅

⸻

③ 相似度评分（替代 yes / no）⭐⭐⭐⭐

这是体验提升的关键。

不要问：能不能匹配

要问：有多像？

⸻

推荐一个简单但非常好用的评分模型

score =
0.4 * normalize 相等

+ 0.3 * token overlap
+ 0.2 * 长度相似度
+ 0.1 * 编辑距离

示例

文本 score
user_name 1.00
userName 0.92
user_name_list 0.78
user_profile 0.31 ❌

👉 你只要设一个阈值，比如 0.75

⸻

编辑距离（Levenshtein）只要最简单版

你甚至可以只用：

1 - (editDistance / maxLength)

不用引第三方库。

⸻

④ 上下文过滤（命中率 > 体验）⭐⭐⭐⭐⭐

这是从“聪明”到“像人”的关键一步。

1️⃣ 限定搜索范围（非常重要）

不要全文扫。

优先顺序：

1. 同一行
2. 同一个段落
3. 同一个代码块 / markdown block
4. 同一个文件

👉 90% 的“想一起改”的文本都在很近的位置

⸻

2️⃣ 编辑时间窗口（官方也这么做）

用户刚改完 3 秒内 → 强预测
超过 10 秒 → 弱预测

时间本身就是一个非常强的“意图信号”

⸻

3️⃣ 排除用户“明确不想改的地方”

比如：
• 光标当前所在行
• 用户刚刚手动修改过的位置
• 上一次点了 Ignore 的区域

⸻

↓

但用户期望的是「同类语义位置的匹配」

二、正确的第一原则（非常重要）

❌ 不要先提高匹配度

✅ 先做「强约束过滤」

三、你现在必须立刻加的「三道硬过滤」（MVP+）

这三条是底线规则，不加体验一定崩。

⸻

✅ 规则 1：必须在「同一文本类别」中匹配（最关键）

你要把编辑位置先分类：

1️⃣ 获取修改位置的 Editor / Document 信息

Editor editor = FileEditorManager.getInstance(project).getSelectedTextEditor();
Document document = editor.getDocument();
int offset = event.getOffset();

⸻

2️⃣ 用最轻量的方式判断「当前文本类型」

⚠️ 不用 PSI，也可以做到 80% 准确
A. 是否在字符串字面量里（Java / Kotlin / JSON 都适用）

boolean isInsideString(String text, int offset) {
int quotes = 0;
for (int i = 0; i < offset; i++) {
if (text.charAt(i) == '"') {
quotes++;
}
}
return quotes % 2 == 1;
}

👉 只要你是在字符串里改的：

❌ 禁止匹配 import / 标识符
✅ 只允许匹配「其他字符串字面量里的文本」

⸻

B. 是否在 import 行（必须直接排除）

boolean isImportLine(Document doc, int offset) {
int line = doc.getLineNumber(offset);
int start = doc.getLineStartOffset(line);
int end = doc.getLineEndOffset(line);
String lineText = doc.getText(new TextRange(start, end));
return lineText.trim().startsWith("import ");
}

👉 规则：

只要修改发生在 import 行
→ 整个预测功能直接 short-circuit（return）

官方也是这么做的。

⸻

✅ 规则 2：匹配目标必须满足「同类位置」

你在找“相似文本”时，不能只看文本，还要看：

修改发生处 允许匹配的目标
字符串字面量 其他字符串字面量
注释 注释
普通代码 普通代码
import ❌ 全部禁止

⸻

示例：字符串 → 字符串（正确）

"USER_NAME"
"USER_NAME_DESC"

示例：字符串 → import（必须禁止）

"com.example.user"
import com.example.user.service.UserService; ❌

⸻

✅ 规则 3：必须是「完整 token」，不能是子串（救命规则）

你现在的问题核心在这里 👇

你改的是字符串的一部分
但匹配的是“任意包含这段字符的地方”

这在 import 里几乎必炸。

⸻

正确规则
如果是字符串内修改：
• 只能匹配 字符串 token 内的完整单元
• ❌ 不能匹配跨 token 的子串

⸻

一个简单但非常有效的做法

boolean isWholeWordMatch(String text, int start, int end) {
if (start > 0 && Character.isJavaIdentifierPart(text.charAt(start - 1))) {
return false;
}
if (end < text.length() && Character.isJavaIdentifierPart(text.charAt(end))) {
return false;
}
return true;
}

👉 import 里的命中几乎都会被这条规则挡掉

四、给你一个「你现在就该用」的匹配流程

用户修改
↓

五、为什么“import 命中”是绝对不可接受的？

这不是你的问题，是所有编辑预测都默认的 UX 共识：
• import 是 结构性语法
• 用户几乎 从不希望“批量同步修改 import”
• JetBrains 官方策略：
import 行 = 非用户表达意图

所以：
👉 直接全局排除是对的，而且是“官方正确”
