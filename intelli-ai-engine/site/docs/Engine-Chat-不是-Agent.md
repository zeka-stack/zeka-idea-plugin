# Engine Chat 不是 Agent

## 问题反馈

有用户反馈 Engine Chat 中无法使用记忆功能。

典型表现是：第一轮对话中用户告诉模型自己的名字，第二轮继续询问“我是谁”或“我叫什么”，模型无法根据上一轮对话回答。

这个现象容易被理解为 Chat 面板没有正确传递上下文，或者多轮对话能力存在缺陷。但从 Engine 的设计定位看，这不是一个需要修复的 bug，而是当前能力边界的一部分。

## 设计说明

Engine Chat 设计上不支持记忆功能。

Engine 的目标不是实现一个完整的开发 Agent，也不是复刻带长期上下文、任务规划、文件检索、工具调用和持久化记忆的 AI 编程助手。

如果用户需要完整 Agent 能力，建议使用更成熟的 AI Agent 工具，例如具备会话记忆、上下文压缩、代码库检索、任务状态管理和工具调用能力的专用产品。

Engine Chat 的定位更轻量：

- 验证设置中配置的 AI 服务商是否可用
- 验证模型、Base URL、API Key、请求参数是否工作正常
- 结合日志输出观察请求、响应、流式输出和错误信息
- 处理一些简单、短上下文、重复性的 AI 辅助工作

因此，不应把 Engine Chat 当成 Agent 使用。它也不具备完整 Agent 所需的上下文管理能力。

## 为什么不默认支持历史记忆

最直接的做法是每次请求都把完整聊天历史传给模型。但这种方式存在明显问题。

首先，token 会持续增长。每轮都附带完整历史时，请求成本和响应延迟会越来越高，最终可能超过模型上下文窗口。

其次，状态管理会复杂化。完整 Agent 不只是“传历史”，还需要处理历史裁剪、摘要、文件上下文、工具调用结果、任务状态和用户偏好。如果只做半套，很容易给用户造成误解，让用户以为
Engine Chat 具备 Agent 能力。

最后，这会偏离 Engine 的定位。Engine Chat 主要用于服务商配置验证和基础调试，不应该承担完整 Agent 的长期上下文管理职责。

## 业内 Agent 如何处理历史上下文

真正的开发 Agent 通常不会简单地把完整历史全部塞进请求，而是使用多层上下文管理机制。

### 短期窗口

Agent 会保留最近若干轮对话，例如最近 6 到 20 条消息。

这种方式可以解决短程上下文问题，例如用户上一轮刚提到变量名、文件名、临时约束或个人信息，下一轮继续追问时模型能够接上。

短期窗口实现简单，但只能覆盖最近上下文，无法解决长期任务记忆。

### 摘要记忆

当历史超过阈值后，Agent 会把较早的对话压缩成摘要，然后丢弃原始消息。

摘要通常保留：

- 当前任务目标
- 用户明确提出的约束
- 已经做过的决策
- 已完成和未完成的步骤
- 关键错误和解决方式

这种方式可以降低 token 消耗，但摘要质量会影响后续推理。如果摘要漏掉关键信息，Agent 仍可能丢失上下文。

### 检索式上下文

开发 Agent 面对代码库时，不会把所有文件都放进上下文，而是按当前问题检索相关代码、文档、日志或历史记录。

常见做法包括：

- 基于关键词搜索相关文件
- 基于语义向量检索相关片段
- 根据错误栈定位代码位置
- 根据当前编辑器、打开文件或用户选区补充上下文

这类机制是开发 Agent 处理大仓库时的核心能力。没有检索能力，只依赖聊天历史，很难稳定完成复杂开发任务。

### 结构化任务状态

成熟 Agent 通常会维护结构化状态，而不是只依赖自然语言聊天记录。

结构化状态可能包括：

- 当前目标
- 当前计划
- 已完成步骤
- 待处理问题
- 当前分支和工作区状态
- 用户偏好
- 关键文件路径
- 最近错误和验证结果

结构化状态比完整聊天记录更稳定，也更节省 token。

### Token Budget

Agent 在每次请求前通常会做 token budget 控制。

一般优先级是：

1. 保留 system prompt 和安全约束
2. 保留当前用户问题
3. 保留最近对话
4. 保留任务摘要
5. 保留检索到的相关文件片段
6. 丢弃最早、最弱相关、价值最低的历史内容

这一步是避免上下文爆炸的关键。

## Engine Chat 的能力边界

Engine Chat 不实现上述完整 Agent 机制。

当前能力边界可以概括为：

- 支持调用已验证的 AI 服务商配置
- 支持选择模型并发送当前输入
- 支持流式输出
- 支持日志面板观察请求链路和错误信息
- 支持有限的文件标签和附件上下文

但它不负责：

- 长期记忆
- 多轮历史压缩
- 代码库级语义检索
- 任务规划
- 自动工具调用
- 跨会话状态持久化
- Agent 式开发工作流

因此，用户在 Engine Chat 中看到“无法记住上一轮对话”的表现，符合当前设计预期。

## 建议说明

如果只是验证服务商是否配置正确、模型是否能正常响应、流式输出是否可用，Engine Chat 是合适的入口。

如果目标是完成复杂开发任务，例如理解整个代码库、连续修改多个文件、维护长期任务状态、自动执行命令并根据结果迭代，就应该使用完整 Agent 工具。

Engine 的定位不是 Agent。Engine Chat 是配置验证和轻量调试入口，不应被当作 Agent 使用。
