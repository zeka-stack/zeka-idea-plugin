## 1 概述

### 1.1 背景

AI 生成提交记录准确率不高的主要原因（约 80%）并非模型问题，而是：

1. **输入噪声过大**：直接将整段 diff 文本丢给模型，包含大量格式化、空白、import 等无意义变更
2. **上下文不完整**：缺少项目模块信息、历史提交风格、变更意图等关键上下文
3. **输出不可控**：模型可能偏离 Conventional Commits 规范，type/scope 判断不准确

### 1.2 设计目标

- ✅ 在变更内容较少时，避免将整文件视为改动
- ✅ 为 AI 提供足够上下文，但不过度扩张提示词
- ✅ 过滤格式化、空白、仅 import 等无意义变更
- ✅ 提升 type/scope/subject 的准确性和一致性

### 1.3 总体思路

1. **变更采集增强**：在 diff 片段上补充类/方法级上下文
2. **去噪过滤**：剔除空白、格式化、仅 import 的变更片段
3. **结构化输出**：变更摘要 + 精简 diff 的分层输入
4. **输出协议化**：先 JSON 校验，再渲染 commit message

## 2 当前实现

### 2.1 核心组件

#### 2.1.1 CodeDiffUtil

**位置**：`intelli-ai-changelog/src/main/java/dev/dong4j/zeka/stack/idea/plugin/changelog/util/CodeDiffUtil.java`

**功能**：

- 从 `Change` 集合中提取代码变更信息
- 生成 Unified Diff 格式的差异内容
- 过滤噪声变更（空白、import、注释、重排）
- 补充 PSI 上下文（类/方法/字段）
- 解析 scope 提示（模块/路径/符号）

**关键特性**：

- 基于行级 diff 片段输出，避免整文件展开
- 每个文件最多 6 个 hunk，每个 hunk 最多 20 行
- 自动识别并过滤无意义变更
- 为 Java 文件补充符号上下文

#### 2.1.2 CodeDiff 模型

**位置**：`intelli-ai-changelog/src/main/java/dev/dong4j/zeka/stack/idea/plugin/changelog/model/CodeDiff.java`

**字段**：

- `filePath`：文件路径
- `changeType`：变更类型（ADD/DELETE/MODIFY/RENAME/MOVE）
- `addedLines`：新增行数
- `deletedLines`：删除行数
- `diffContent`：Unified Diff 格式内容
- `scopeHint`：建议的 scope（模块名/路径/符号名）

### 2.2 实现细节

#### 2.2.1 变更类型识别

```java
private static CodeDiff.ChangeType determineChangeType(Change change) {
    ContentRevision before = change.getBeforeRevision();
    ContentRevision after = change.getAfterRevision();

    if (before == null && after != null) return ADD;
    if (before != null && after == null) return DELETE;
    if (before != null && !before.getFile().getPath().equals(after.getFile().getPath())) {
        return RENAME;
    }
    return MODIFY;
}
```

#### 2.2.2 去噪过滤规则

已实现的过滤规则：

- **空白变更**：`isWhitespaceOnlyChange()` - 仅空白字符变化
- **Import 变更**：`isImportOnlyChange()` - 仅 import 语句变化
- **注释变更**：`isCommentOnlyChange()` - 仅注释内容变化（Java 文件）
- **重排变更**：`isReorderOnlyChange()` - 仅代码顺序调整（Java 文件）

#### 2.2.3 PSI 上下文补充

通过 `ContextResolverRegistry` 解析符号上下文：

- 类名、方法名、字段名
- 变更片段所属的代码结构
- 在 diff 中标注：`上下文: ClassName#methodName`

#### 2.2.4 Scope 解析策略

优先级顺序：

1. **模块名**：`ModuleUtilCore.findModuleForFile()` 获取 Maven/Gradle 模块
2. **路径作用域**：从文件路径解析（跳过 src/main/java 等常见根目录）
3. **主要符号**：通过 PSI 解析类名/函数名

最终标准化为 kebab-case 格式。

## 3 核心功能

### 3.1 变更采集增强

#### 3.1.1 行级 Diff 片段提取

- 使用 IntelliJ Platform 的 `ComparisonManager` 进行行级比较
- 每个文件最多提取 6 个 hunk（变更片段）
- 每个 hunk 最多包含 20 行变更
- 自动跳过无意义的变更片段

#### 3.1.2 PSI 上下文补充

为每个变更片段补充代码结构上下文：

```
@@ -10,5 +10,8 @@
上下文: UserService#findById
-public User findById(int id) {
+public User findById(int id) throws UserNotFoundException {
     return userRepository.findById(id);
 }
```

### 3.2 去噪过滤机制

#### 3.2.1 过滤规则

| 规则        | 检测方法                       | 适用文件类型 |
|-----------|----------------------------|--------|
| 空白变更      | `isWhitespaceOnlyChange()` | 所有     |
| Import 变更 | `isImportOnlyChange()`     | 所有     |
| 注释变更      | `isCommentOnlyChange()`    | Java   |
| 重排变更      | `isReorderOnlyChange()`    | Java   |

#### 3.2.2 过滤逻辑

```java
// 在生成 diff 时应用过滤
if (isWhitespaceOnlyChange(beforeChanged, afterChanged)) continue;
if (isImportOnlyChange(beforeChanged, afterChanged)) continue;
if (isJavaFile && isCommentOnlyChange(beforeChanged, afterChanged)) continue;
if (isJavaFile && isReorderOnlyChange(beforeChanged, afterChanged)) continue;
```

### 3.3 结构化输出

#### 3.3.1 Prompt 构建流程

1. **提取 CodeDiff 列表**：从 `Change` 集合提取
2. **构建变更文本**：格式化每个文件的变更信息
3. **限制长度**：最多 30 个文件，总长度不超过 10,000 字符
4. **补充上下文**：添加最近 3 条提交记录、用户补充说明

#### 3.3.2 输出格式

```
文件: src/main/java/UserService.java
变更类型: MODIFY
建议scope: user-service
新增行数: 5
删除行数: 2
变更内容:
@@ -10,5 +10,8 @@
上下文: UserService#findById
-public User findById(int id) {
+public User findById(int id) throws UserNotFoundException {
     return userRepository.findById(id);
 }
```

## 4 优化策略

### 4.1 输入优化（已实现）

#### 4.1.1 ✅ 只取实际要提交的变更

- 使用 `ChangeListManager` 获取当前 changelist 的变更
- 避免包含临时调试、格式化、无关文件
- 支持按 included changes 生成

#### 4.1.2 ✅ Diff 结构化摘要

- 每个文件输出结构化信息：路径、类型、增删行数、scope 提示
- 使用行级 diff 片段，而非整文件内容
- 补充 PSI 上下文，标注变更所属的代码结构

#### 4.1.3 ✅ 过滤噪声

- 自动识别并过滤空白、import、注释、重排变更
- 统计非空白行变更比例
- 标记噪声文件，在 prompt 中明确说明

### 4.2 上下文补齐（部分实现）

#### 4.2.1 ✅ 最近提交记录

- 获取最近 3 条提交记录作为风格参考
- 在 prompt 中明确标注"仅用于风格和上下文参考"

#### 4.2.2 ⚠️ 项目模块信息（待优化）

**当前实现**：

- 通过 `ModuleUtilCore` 获取模块名作为 scope 提示
- 从文件路径解析路径作用域

**优化方向**：

- 结构化解析历史提交的 type/scope/subject
- 统计高频 scope，帮助模型推断
- 明确项目约定（如 scope 优先用模块名）

### 4.3 输出控制（待实现）

#### 4.3.1 ⚠️ JSON 协议化输出

**建议实现**：

```json
{
  "type": "feat|fix|refactor|docs|test|chore|perf|build|ci|style|revert",
  "scope": "string (<=20, kebab-case)",
  "subject": "string (<=72, imperative, no period)",
  "body": "string (optional, explain why/impact)",
  "breaking": false
}
```

**校验规则**：

- JSON 解析失败 → 自动重试一次
- type 不在枚举 → 回退为 `chore` + 推断 scope
- subject 超长/含句号/含类名方法名 → 自动修剪或重写

#### 4.3.2 ⚠️ 两段式生成

**Step A：意图抽取**

```json
{
  "main_intent": "...",
  "affected_areas": ["auth", "api"],
  "key_changes": ["...", "..."],
  "breaking": false,
  "suggested_type": "fix",
  "suggested_scope": "auth"
}
```

**Step B：根据 Step A + 精简 diff 生成最终 commit**

### 4.4 规则化分类（待实现）

#### 4.4.1 建议规则

- `test/**`、`*Test*` → `type: test`
- 只改文档 → `type: docs`
- 只改格式化/import → `type: style/chore`
- 变更集中在某个 module → `scope: module`
- 有 API 签名变化 → 标记 `breaking: true`

**优势**：AI 最容易飘的就是 type/scope，规则化锁定这两项，AI 只负责 subject/body 会稳定很多。

## 5 多仓库支持

### 5.1 问题场景

一个 IDEA 窗口中有多个 Git root，一次改动跨了多个仓库。

### 5.2 处理策略

#### 5.2.1 按 VCS Root 分组生成（推荐）

**实现步骤**：

1. 统计当前 included changes 涉及多少个 Git root
2. 如果 `roots.size() > 1`，按 root 分组生成 N 份 commit message
3. 在 UI 上提示用户："本次变更涉及 N 个仓库：A、B。建议拆分提交"

**适用场景**：

- 多 repo 同项目（多 module 各自一个仓库）
- repo 嵌套（上层 repo + 子目录独立 repo）
- 同时打开多个相关仓库作为 modules

#### 5.2.2 提供 3 个可选动作

当检测到跨仓库时：

1. **Split by Repository（推荐）**
    - 自动创建 `repoA - <task>`、`repoB - <task>` 两个 changelist
    - 把 change 移进去，让用户逐个提交

2. **Commit Separately（推荐）**
    - 不改 changelist，仅在 Commit UI 中按目录/根目录选择变更并提交

3. **Commit Together（不推荐，但允许）**
    - 生成一条"跨仓库总括"的 message
    - 例如：`chore(sync): align configs across repos`
    - 在 body 里列出 repoA/repoB 的摘要

#### 5.2.3 实现要点

**A) 获取 VCS Root**

```java
ProjectLevelVcsManager vcsManager = ProjectLevelVcsManager.getInstance(project);
Map<VirtualFile, List<Change>> rootToChanges = new HashMap<>();

for (Change change : changes) {
    VirtualFile root = vcsManager.getVcsRootFor(change.getVirtualFile());
    rootToChanges.computeIfAbsent(root, k -> new ArrayList<>()).add(change);
}
```

**B) 处理仓库初始化时机**

- Git root / GitRepository 初始化是异步的
- 建议使用：
    - `post-startup activity` 再初始化一次
    - 监听 `VcsRepositoryManager#VCS_REPOSITORY_MAPPING_UPDATED` 事件
    - 在后台线程调用 `GitRepositoryManager#getRepositoryForRoot` 触发等待初始化

**C) 产品化体验**

默认检测到跨仓库时：

- 顶部红/黄提示：涉及 N 个仓库
- 展示每个仓库一条建议 commit message（可一键复制/应用）
- 提供按钮：Split by Repository / Commit Together / Cancel

## 6 未来规划

### 6.1 短期优化（高优先级）

#### 6.1.1 结构化摘要增强

在 `CodeDiffUtil` 产出的片段基础上，增加"文件级摘要"：

- 模块/变更类型/关键行为变化
- 先于 diff 输入，帮助 AI 理解意图
- 最多 3 条变更要点，禁止实现细节

#### 6.1.2 语义去噪扩展

- 增加"仅注释变更""仅重排变更"的识别（已部分实现）
- 当文件全为噪声时直接剔除
- 统计噪声比例，在 prompt 中明确标注

#### 6.1.3 Scope 归一化

- 基于 PSI/模块路径推断 scope
- 优先级：模块名 > 功能域 > 类名
- 标准化为 kebab-case（已实现）

#### 6.1.4 输出协议化

- 要求模型先输出 JSON（type/scope/subject/body/breaking）
- 解析失败自动重试
- 规则校验和修正

### 6.2 中期优化（中优先级）

#### 6.2.1 两段式生成

- Step A：意图抽取 JSON
- Step B：根据 JSON + 精简 diff 生成最终 commit message

#### 6.2.2 变更片段压缩

- 限制每个文件的片段数量与长度
- 防止大文件噪声淹没有效信息
- 当前已实现：最多 6 个 hunk，每个 hunk 最多 20 行

#### 6.2.3 基于历史的相似提交检索（RAG）

- 对本次变更做本地摘要
- 用摘要检索历史提交（同模块、同类名、同关键词）
- 把 Top K 历史提交 message + 摘要当 few-shot 示例

### 6.3 长期优化（低优先级）

#### 6.3.1 多候选 + 置信度

- 给用户 3 个备选：
    - 候选 A：偏保守（chore/refactor）
    - 候选 B：偏功能（feat/fix）
    - 候选 C：偏影响说明（带 body）
- 用规则打分（噪声比例、API 变更、配置变更），默认选最高分

#### 6.3.2 可测试化

- 补充最小样例的单测
- 覆盖"空白/仅 import/注释/重排/小改动"场景
- 验证去噪过滤的正确性

#### 6.3.3 Prompt 优化

**当前规则**：

- subject 禁止出现：类名/方法名/变量名/具体字段名（除非它是领域名）
- body 才允许提关键名词（最多 2 个）
- 如果 diff 主要是格式化/注释/import 调整，type 必须是 `style` 或 `chore`，且 subject 必须说明"no functional change"

**优化方向**：

- 更明确的格式要求
- 更严格的校验规则
- 更好的错误提示

## 8 附录

### 8.1 代码示例

#### 8.1.1 获取当前 Changelist 的变更

```java
ChangeListManager clm = ChangeListManager.getInstance(project);
LocalChangeList changeList = clm.getDefaultChangeList();
Collection<Change> changes = changeList.getChanges();
```

#### 8.1.2 按 VCS Root 分组

```java
ProjectLevelVcsManager vcsManager = ProjectLevelVcsManager.getInstance(project);
Map<VirtualFile, List<Change>> rootToChanges = new HashMap<>();

for (Change change : changes) {
    VirtualFile file = change.getVirtualFile();
    if (file != null) {
        VirtualFile root = vcsManager.getVcsRootFor(file);
        rootToChanges.computeIfAbsent(root, k -> new ArrayList<>()).add(change);
    }
}
```

#### 8.1.3 生成 CodeDiff 列表

```java
List<CodeDiff> codeDiffs = CodeDiffUtil.extractCodeDiffs(changes);
```

### 8.2 配置说明

#### 8.2.1 提示词模板占位符

- `{codeDiffs}`：代码变更信息（格式化的 CodeDiff 列表）
- `{recentCommits}`：最近 3 条提交记录
- `{extraContext}`：用户补充说明（可选）

#### 8.2.2 系统提示词

位置：`SettingsState.getDefaultCommitMessageSystemPrompt()`

包含：

- AI 角色设定（代码审查专家）
- Conventional Commits 规范要求
- 分析与表达原则
- 正文书写规则
