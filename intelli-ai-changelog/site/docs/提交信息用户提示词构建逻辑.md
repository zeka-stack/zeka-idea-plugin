# 提交信息用户提示词构建逻辑

本文说明提交信息（commit message）生成时，**用户提示词**从生成到兜底的全链路处理逻辑，帮助插件开发者快速理解 changelog 插件如何在“保证有效上下文”的前提下控制长度，避免因超长导致提交消息生成失败。

## 概览

用户提示词由三大块拼接而成（模板中占位符）：

1. `{codeDiffs}`：结构化上下文 JSON（最重要，包含文件级 diff）
2. `{rawPatch}`：IDEA 原生 patch（可选补充，可能很长）
3. `{diffSummary}`：降噪摘要（可选辅助）

对应的默认模板在：

- `intelli-ai-changelog/src/main/java/dev/dong4j/zeka/stack/idea/plugin/changelog/settings/SettingsState.java`
  - `getDefaultCommitMessageUserPrompt()`

## 构建链路总览

入口调用：

- `ChangelogPromptBuilder#buildCommitMessagePrompt(...)`

内部流程（简化）：

1. 通过 `ChangelogCommitDiffBuilder` 构建 `DiffPayload`
2. 由 `ChangelogPromptBuilder` 拼装三大块内容并替换模板占位符
3. 在提交消息场景启用“分段兜底 + 全局兜底”控制总长度

## 一、{codeDiffs}：结构化上下文 JSON

**生成方法：**

- `ChangelogPromptBuilder#buildStructuredContext(...)`

**数据来源：**

- `ChangelogCommitDiffBuilder#buildCodeDiffPayload(...)` 或 `buildIdeaPatchDiffPayload(...)`
- `CodeDiffUtil#extractCodeDiffs(...)` 生成 `List<CodeDiff>`

**核心字段：**

- `project.*` / `statistics.*` / `metadata.*`：项目与统计信息
- `changes[*]`：文件级变更
  - `full_diff_content`：来自 `CodeDiffUtil` 生成的 diff 内容（最重）

**超长风险：**

- `changes[*].full_diff_content` 体积最大
- 当文件较多或单文件 diff 很长时，JSON 体积显著膨胀

## 二、{rawPatch}：IDEA 原生 patch

**生成方法：**

- `ChangelogCommitDiffBuilder#buildPatchText(...)`
  - 内部使用 `IdeaTextPatchBuilder.buildPatch(...)` 生成 patch

**启用条件：**

- `SettingsState.CommitMessageDiffProvider` 为 `IDEA_PATCH` 或 `AUTO`
- `AUTO` 视文件数量决定是否使用 IDEA patch

**超长风险：**

- patch 为完整文件差异，可能比 `{codeDiffs}` 更长

## 三、{diffSummary}：降噪摘要

**生成方法：**

- `ChangelogPromptBuilder#buildDiffSummaryText(...)`

**来源：**

- 基于 `CodeDiffUtil` 输出与 `DiffPayload` 元数据构建
- 会对文件数、字符数进行限制

**超长风险：**

- 低于 `{rawPatch}` 与 `full_diff_content`，但仍可能在文件数多时增长

## 长度控制的完整链路（核心优化点）

以下链路按执行顺序串联，覆盖“内容生成 → 分段兜底 → 全局兜底 → 日志输出”的完整流程：

### 1) 代码 diff 生成与降噪

- 入口：`CodeDiffUtil#extractCodeDiffs(...)`
- 关键策略：
  - 只要是文本文件有变更，就生成 diff
  - 统一做 hunk/行数/单行长度限制
  - 单文件 diff 超出上限会截断（避免单文件占满上下文）
- 目标：让每个文件都有可用 diff，同时控制单文件体积

### 2) DiffPayload 组装

- 入口：`ChangelogCommitDiffBuilder#buildCodeDiffPayload(...)` / `buildIdeaPatchDiffPayload(...)`
- 产出内容：
  - `codeDiffs`：结构化 diff（来自 `CodeDiffUtil`）
  - `rawPatch`：IDEA patch（可选补充）
  - `diffSummary`：降噪摘要

### 3) 分段兜底（避免单段过长）

- 入口：`ChangelogPromptBuilder#buildCommitMessagePromptWithFallback(...)`
- 当前策略：
  - `rawPatch` 按行数截断（`MAX_RAW_PATCH_LINES`）
  - `diffSummary` 按行数截断（`MAX_DIFF_SUMMARY_LINES`）
- 目标：避免单段内容无限膨胀，优先保留“更重要”的结构化 JSON

### 4) 全局兜底（防止整体超长）

- 入口：`ChangelogPromptBuilder#buildCommitMessagePromptWithFallback(...)`
- 策略：逐级降级 + 硬截断
  1. 完整 `codeDiffs + rawPatch + diffSummary`
  2. 去掉 `rawPatch`
  3. 去掉 `diffSummary`
  4. 降级结构化 JSON（减少文件数 + 缩短单文件 diff）
  5. 最终硬截断（`MAX_COMMIT_MESSAGE_PROMPT_HARD_CHARS`）
- 目标：即使极端大改动，也能保证请求可发送

### 5) 控制台日志输出兜底（仅日志）

- 入口：`ChangelogAiExecutor#logChangelogRequest(...)`
- 特性：
  - **仅影响控制台日志**，不影响实际请求内容
  - 对 `User Prompt` 日志做“保留 JSON 首尾、省略 changes 中间”的裁剪
  - 避免日志因超长截掉 JSON 尾部

## 重要说明：控制台日志与真实请求

控制台日志输出与真实请求不同步裁剪：

- 控制台输出：`ChangelogAiExecutor#logChangelogRequest(...)`
  - `promptLogMaxLength` 控制日志长度
- 真实请求：不受控制台日志裁剪影响

## 可控优化点（供后续参考）

- 降低 `rawPatch` 权重，或在日志中替换为占位
- 控制 `full_diff_content` 单文件长度与总文件数
- 对 `diffSummary` 做更激进裁剪
