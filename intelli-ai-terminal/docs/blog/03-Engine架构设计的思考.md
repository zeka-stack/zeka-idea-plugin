# Engine 架构设计的思考

> Engine 的存在，是为了让插件保持简单。而插件保持简单，是为了让用户保持信任。

当我在开发 IntelliAI 插件系列时，很快就遇到了一个问题：**AI 能力本身不应该和具体功能插件强耦合。**

这就是为什么我设计了 Engine 这个独立的底层组件。

## 为什么需要 Engine

随着插件能力的演进，我很快意识到一个问题：

如果每一个插件都各自管理：

- 模型接入
- Prompt 调度
- Token 统计
- API 兼容
- 失败处理

那么最终结果一定是：

- 重复代码
- 行为不一致
- 难以维护
- 难以扩展

因此，我将 AI 能力抽象为一个独立的底层组件：**Engine**。

## Engine 的核心定位

Engine 是 AI 能力的基础设施，而不是功能提供者。

它的职责不是"做什么"，而是"如何做"。

### Engine 负责什么（明确）

Engine 只负责以下通用能力：

- ✅ 模型与服务商管理（OpenAI / Claude / Gemini / 兼容 API）
- ✅ Prompt 执行与上下文拼装
- ✅ 请求生命周期管理
- ✅ Token / 使用量统计
- ✅ 错误与超时处理
- ✅ 能力抽象与统一接口

这些能力具有明显特征：

- 与具体业务无关
- 可被多个插件复用
- 不直接影响用户交互

### Engine 明确不负责什么

Engine 不负责：

- ❌ UI 展示
- ❌ 交互设计
- ❌ 业务决策
- ❌ 上下文语义判断
- ❌ 用户操作流程

换句话说：

> Engine 不知道"用户在做什么"，它只知道"如何正确调用 AI"。

## Engine + 单一插件的协作模式

我采用如下分层结构：

```
[ Engine ]
   ↑
[ Focused Plugin ]
   ↑
[ User Interaction ]
```

- **Engine**：稳定、可复用、低变更
- **插件**：小而专注、快速迭代
- **用户**：无需感知 Engine 的存在

这种设计的核心思想是：**关注点分离**。

### 关注点分离的好处

#### 1. 插件可以自由演进

- Terminal 插件：专注于命令生成
- Javadoc 插件：专注于文档生成
- Changelog 插件：专注于变更日志生成

它们共享 Engine，但互不影响。

#### 2. 用户信任模型更清晰

- **Engine**：能力底座
- **插件**：问题解法

用户不会因为一个插件的行为，而质疑整个系统。

## 这种设计的长期价值

### 1. 技术价值

**降低重复代码**

所有 AI 相关的通用能力都在 Engine 中实现一次，所有插件复用。这意味着：

- Bug 修复只需要在一个地方
- 新功能添加只需要在一个地方
- API 兼容性处理只需要在一个地方

**保证行为一致性**

所有插件都通过 Engine 调用 AI，保证了：

- 错误处理方式一致
- 日志记录格式一致
- 统计信息收集一致

### 2. 产品价值

**清晰的职责边界**

当用户遇到问题时，可以很清楚地知道：

- 如果是 AI 调用问题 → Engine 的责任
- 如果是业务逻辑问题 → 插件的责任

这种清晰的边界，让用户更容易理解、信任系统。

**易于扩展**

当我想添加新的插件时：

- 不需要重新实现 AI 调用逻辑
- 只需要专注于业务逻辑
- Engine 的能力自动继承

### 3. 商业价值

**降低维护成本**

- Engine 维护一次，所有插件受益
- 插件可以专注于自己的核心功能
- 技术债务更容易管理

**提高用户信任**

- 清晰的架构让用户更容易理解系统
- 单一职责的插件更容易被信任
- 基础设施的稳定性让用户更有信心

## 一个实际的例子

让我用一个实际的例子来说明这种设计的优势。

假设我现在要添加一个新插件：**Code Review 插件**。

**如果每个插件都自己实现 AI 调用：**

1. 我需要重新实现模型接入
2. 我需要重新实现错误处理
3. 我需要重新实现 Token 统计
4. 我需要处理 API 兼容性
5. 我需要处理流式响应
6. ... （无数重复工作）

**使用 Engine 架构：**

1. 我只需要专注于 Code Review 的业务逻辑
2. 调用 `engine.generateContent()` 即可
3. Engine 自动处理所有底层细节

**开发时间从 2 周缩短到 2 天。**

## 架构决策的思考

很多人问我：为什么不把 Engine 的功能直接放在每个插件里？

我的回答是：**这不是技术问题，而是架构思维的问题。**

当一个系统有多个插件时，就有两个选择：

### 选择 1：每个插件独立实现

```
[ Plugin A ] - AI 调用逻辑
[ Plugin B ] - AI 调用逻辑（重复）
[ Plugin C ] - AI 调用逻辑（重复）
```

问题：

- 代码重复
- 行为不一致
- 维护困难

### 选择 2：抽象公共能力

```
[ Engine ] - AI 调用逻辑（一次实现）
   ↑
[ Plugin A ]
[ Plugin B ]
[ Plugin C ]
```

优势：

- 代码复用
- 行为一致
- 易于维护

这不是什么高深的架构模式，只是最基本的 **DRY 原则**（Don't Repeat Yourself）。

但我发现很多工具开发者都会忽略这一点，因为他们只关注单个插件，而忽略了整个系统的设计。

## 结论

Engine 的存在，是为了让插件保持简单。

而插件保持简单，是为了让用户保持信任。

这是一个从架构角度做出的产品决策，而不是技术炫技。

当你理解了这种设计的价值，你就会明白为什么我宁愿花时间设计 Engine，也不愿意快速堆砌功能。

**好的架构，是长期价值的体现。**
