# 为什么我不做大而全的 AI 工具

> 如果一个工具需要你"学习它"，那它已经偏离了工程师工具的初衷。

当我在设计 IntelliAI Terminal 时，很多人问我：为什么不做一个像 Claude Code 或 Codex 那样功能强大的 AI CLI 工具？

我的回答很简单：**我们不做"大而全"的 AI CLI 工具，而是做"刚好解决一个痛点"的 IDE 内工具。**

## 这不是功能强弱的问题

先澄清一个误解：这不是"功能强弱"的问题，而是"设计目标完全不同"的问题。

| 维度   | 大而全 CLI（Claude Code / Codex / Gemini CLI） | 我的插件                |
|------|-------------------------------------------|---------------------|
| 产品目标 | AI 开发助手 / 平台                              | 终端命令生成              |
| 使用场景 | 长任务 / 复杂交互                                | 高频、即时、小动作           |
| 侵入性  | 高（新工具、新心智）                                | 几乎为 0               |
| 学习成本 | 需要理解命令体系                                  | 不用学                 |
| 上下文  | 由工具维护                                     | 来自真实 IDE & Terminal |
| 失败成本 | 高（跑偏、误操作）                                 | 低（只是补全一行命令）         |

## 大而全工具在终端场景下的现实问题

让我用真实场景来说明。

### 场景对比

**我要查一个 Docker 容器日志**

使用大而全 CLI 工具：

1. 切换到 Claude Code
2. 描述当前环境（我在什么项目、什么目录）
3. 等它生成一堆解释
4. 从输出中找到命令
5. 拷贝命令
6. 回到终端执行

**使用我的插件：**

```
# 查看 docker 容器日志
[Tab]
完成。
```

没有上下文切换，没有角色切换，没有心理切换。

### 80% 的终端操作其实很简单

以 Claude Code / Codex 为例：

- 它们擅长：写代码、改工程、执行多步任务

但在真实工程日常中：

- **80% 的终端操作是：查、看、清、跑**
- 是一次性、短命令、高频操作

为了这一行命令，你需要：

- 切换到 CLI 工具
- 进入它的交互模式
- 描述上下文
- 再拷回终端

成本远高于收益。

## 工程师真正需要的

我在开发这个插件时，反复问自己：**工程师真正需要的是什么？**

答案是：

> "我现在在敲命令，别打断我。"

我的插件的哲学是：

- ✅ 不接管终端
- ✅ 不重写工作流
- ✅ 不引入新概念
- ✅ 不让用户"进入 AI 模式"

而是：

> **在原本的肌肉记忆上，轻轻推一把。**

## 核心价值：低认知负担

这是我和所有大模型 CLI 工具的分水岭。

当一个工具失败时，它会不会让我更麻烦？

- **大而全工具失败**：可能改了代码、可能执行了命令、回滚成本高
- **我的插件失败**：最多就是没补全一行命令

这叫"安全失败（Fail Safe）"。

## 专注的真正含义

我说"我更愿意使用具有单一功能的工具"，这并不意味着：

❌ 功能弱
❌ 能力不足

而是：

✅ 功能边界清晰
✅ 行为可预测
✅ 失败成本可控

这就像支付宝的例子。支付宝最开始是做支付的，但现在掺杂了非常多的功能。虽然功能强大，但用户心理负担也在增加：

- 这个功能在哪里？
- 这个功能安全吗？
- 我需要的功能被埋在哪里？

**工具应该让人专注于任务本身，而不是工具的使用方式。**

## Engine 独立：一个高级的设计信号

我把 AI Engine 独立出来作为一个基础设施层，然后围绕它构建各种功能单一但能直击痛点的插件。

大多数工具的做法：

- 一个插件
- 一个 AI
- 一个入口
- 所有功能堆进去

结果是：

- 配置复杂
- 行为不可控
- 用户不知道"它到底擅长什么"

我的做法：

- **Engine**：模型管理、Prompt 执行、统计 & 能力抽象
- **插件**：单一职责、极小心智、即插即用

这在理念上更接近：

- Unix 工具哲学
- JetBrains 自己的插件生态

我可以非常自信地说：

> Engine 是能力底座，插件是问题解法。

## 我的价值主张

我帮你整理了一段非常克制、非常工程师向的说明：

Claude Code、Codex 和 Gemini CLI 是功能强大的 AI 工具，适合复杂任务和深度交互。

但在日常开发中，大多数终端操作只是一些高频、短小、即时的命令。

我的插件不试图取代这些工具，而是专注解决一个简单的问题：

> **在你已经打开的终端里，用最小的干扰生成正确的命令。**

没有新的工作流，没有新的学习成本，只是让你更快完成正在做的事情。

## 一句话总结

大而全的 AI 工具解决"复杂问题"，我的插件解决"你此刻正在做的这一步"。

这不只是产品定位，更是一种工具观：

**Less is More。**
