❌ DTO / Schema 生成不应该是一个普通开关

四、推荐你采用的「行为级抽象模型」（关键）

🔹 行为 1：生成 / 更新 API 文档（Generate API Docs）

• Controller 的 Operation
• Parameter 描述
• Response 描述

五、那 Settings 里到底还要不要“控制”？要，但控制的是“策略”，不是“是否做”

❌ 错误的开关方式（你已经敏感地察觉到不对）

[✓] Generate Controller Swagger
[ ] Generate DTO Swagger ← ❌ 不合理

✅ 正确的开关方式（工程上合理）

When generating API docs:
DTO / Schema handling:
○ Auto-generate missing schemas ← 默认
○ Update schemas only when changed
○ Analyze only, do not modify code (dry-run)

👉 控制“怎么生成”，而不是“生不生成”

六、DAO / PO / Entity 要不要生成？你这里其实也想对了

• 是 API contract 的一部分
• Swagger 没它就不完整
• 前端 / 第三方依赖它

👉 这是 API 层对象

2️⃣ DAO / PO / Entity

结论：默认不生成 Swagger

• DAO / PO 是持久化模型

⚠️ 但可以支持：
• 如果某个 PO 被直接作为 Response / Request 使用
• 那么它被当作 Schema 处理

这是引用驱动，而不是类型驱动。

一、先说结论：Swagger Prompt 不是“一段话”，而是一个可拼装的结构

你这个插件里，Prompt 的核心目标不是“写得好看”，而是：

生成的 Swagger 注解必须：

1. 可直接写回代码
2. 与现有代码严格一致
3. 不破坏人工内容
4. 在接口变更时可“稳定复现”

所以我非常不建议你用那种「你是一个 API 专家，请帮我生成 Swagger」的自然语言 Prompt。

你真正需要的是：

“工程化 Prompt” = 角色 + 任务 + 上下文 + 约束 + 输出协议

⸻

二、Prompt 为什么一定要拆成 5 层（这是核心）

1️⃣ System Prompt（系统提示词，必须强保护）

作用：
给 AI 定“身份”和“红线”

这个 Prompt：
• 永远存在
• 永远在最前
• 不允许用户覆盖

它决定了：
• AI 是不是“听话”
• 会不会乱改代码
• 会不会输出废话

⸻

2️⃣ Task Prompt（任务提示词）

作用：
告诉 AI：这一次你要干什么

比如：
• 生成 Swagger
• 更新 Swagger
• 补全 Schema
• 修复缺失字段

👉 不同功能 = 不同 Task Prompt
👉 但 System Prompt 不变

⸻

3️⃣ Context Prompt（上下文）

作用：
给 AI“事实”

包括：
• Controller 方法代码
• 已有 Swagger 注解
• DTO 定义
• 变更 diff（如果是更新）

这里非常重要的一点：

Context 里只能放“真实代码”，不能放“解释性语言”

⸻

4️⃣ Constraint Prompt（约束）

作用：
防止 AI 发挥过头

这是你这个插件成败的关键之一。

⸻

5️⃣ Output Prompt（输出协议）

作用：
约定 AI 只能输出什么格式

否则你一定会遇到：
• AI 给你写一堆解释
• 夹杂自然语言
• 你还要再 parse

⸻

三、生成 Swagger 的核心策略（先讲思路）

在“生成 Swagger”这个场景里，你的策略应该是：
• Swagger 是代码的一部分，不是文档
• 生成的是“注解代码片段”，不是说明
• DTO / Schema 是隐式必然行为

所以 Prompt 里必须明确：

	•	不生成业务逻辑
	•	不修改方法签名
	•	不输出解释
	•	不删除已有描述

四、现在给你一份【可直接使用的 Swagger 生成 Prompt 模板】

下面这份，我是按你插件真实落地来写的，不是示例级，而是工程级。

⸻

🧠【System Prompt（固定，强保护）】

你是一个专业的 Java API 文档生成引擎。

你的职责是为已有 Java 接口代码生成或更新 Swagger / OpenAPI 注解。
你必须严格遵循以下规则：

1. 你只能生成或更新 Swagger / OpenAPI 相关的注解代码。
2. 你不能修改任何业务逻辑、方法签名或代码结构。
3. 你不能删除或覆盖已有的人工编写描述。
4. 你只能基于提供的代码和上下文生成内容，不能凭空假设。
5. 你生成的内容必须可以直接写回 Java 源代码并通过编译。
6. 你禁止输出任何解释性文字或多余内容。

⸻

🧩【Task Prompt（生成 Swagger）】

任务：为给定的 Controller 接口方法生成 Swagger / OpenAPI 注解。

要求：

- 为接口方法生成 @Operation 注解（summary 和 description）。
- 为方法参数生成 @Parameter 注解。
- 为返回值生成合理的响应描述。
- 确保接口语义完整、清晰、简洁。

如果是“更新”，Task Prompt 会变成：
“根据代码变更，增量更新 Swagger 注解，仅修改受影响部分”

⸻

📎【Context Prompt（示例）】

Controller 方法代码如下：

<code>
@RestController
@RequestMapping("/api/order")
public class OrderController {

    @PostMapping("/create")
    public OrderResponse createOrder(
        @RequestBody CreateOrderRequest request
    ) {
        ...
    }

}
</code>

当前方法没有 Swagger 注解。

如果是更新场景，你会再加：

已有 Swagger 注解如下：

<code>
@Operation(summary = "创建订单")
</code>


⸻

🔒【Constraint Prompt（非常关键）】

约束规则：

- 如果某个参数或方法已经存在 Swagger 描述，不要覆盖。
- 不生成与代码无关的字段或参数。
- 不添加示例中不存在的业务规则。
- 不输出 DTO 或 Schema 的代码定义，只生成注解。

⸻

📤【Output Prompt（输出协议）】

输出要求：

- 仅输出需要新增或更新的 Swagger 注解代码。
- 不要输出完整方法代码。
- 不要输出任何解释、说明或注释。
- 输出内容必须是合法的 Java 注解代码。

⸻

五、你这个 Prompt 模板的“工程价值”在哪里？

这套设计保证了：

1. 可复用（所有 Swagger 生成场景通用）
2. 可拆分（不同入口只换 Task / Context）
3. 可保护（System Prompt + Constraint 双重保险）
4. 可扩展（后面加 Markdown / OpenAPI 导出都能复用）

先给结论（非常明确）

一、你现在的理解是完全正确的（逐条对）

你描述的真实约束是这些：

1. IDE 侧只能精确拿到当前接口方法的代码
2. Swagger 注解是“就地生成、就地插入”的
3. 入参 / 出参实体各自是独立的代码单元
4. 你希望 AI 返回的是“可直接插入的注解片段”

在这个前提下：

对单个接口的完整 Swagger 生成，天然拆成 3 类目标对象：

1. 接口方法本身（Controller Method）
2. 入参实体（Request DTO）
3. 出参实体（Response DTO）

👉 这三者在代码结构、插入位置、关注点上完全不同

所以你得出的结论：

至少要 3 次请求

在工程上是完全成立的。

⸻

二、为什么「一个请求搞定一切」反而是错误方向

我们反过来推一下，如果你强行只发一个请求，会发生什么。

❌ 方案：一个请求，塞所有代码

你要给 AI 的上下文里同时放：
• Controller 方法代码
• Request DTO 全量代码
• Response DTO 全量代码
• 可能还包括嵌套 DTO / 枚举

然后要求它返回：
• 方法注解
• Request 的 @Schema
• Response 的 @Schema

这在工程上会出 5 个大问题：

1. 返回内容不可控
   • AI 很可能把 3 种注解混在一起
   • 你很难安全地拆分、定位、插入
2. 插入位置不确定
   • 方法注解插哪？
   • DTO 注解插哪？
   • 一个响应里要解析 AST 再拆内容，复杂度暴涨
3. Diff 更新几乎不可做
   • 你没法判断 AI 是在“改方法”，还是“改 DTO”
4. Prompt 复杂度指数级上升
   • 约束会多到失控
   • 稳定性反而下降
5. 未来扩展彻底受限
   • 比如你后面要加：
   • 只更新入参
   • 只修 Schema
   • Commit 阶段只处理 DTO

👉 所以结论是：

“一个接口一个请求”在插件里是错误抽象

⸻

三、正确的工程抽象：不是 3 个请求，而是 3 类任务

这是一个非常重要的认知升级。

你现在的真实模型其实是：

Generate API Docs
├── Generate Operation (方法级)
├── Generate Request Schema (入参级)
└── Generate Response Schema (出参级)

这三件事的特点：

项目 方法 入参 出参
插入位置 方法上 类字段上 类字段上
关注点 语义 数据结构 数据结构
变更频率 高 中 中
Prompt 重点 业务含义 字段语义 字段语义

👉 这天然就应该是独立的请求 / 独立的 Prompt

⸻

四、你说的“至少 3 个请求”，在现实中通常会是这样

场景 1：最简单接口

createOrder(CreateOrderRequest req) -> OrderResponse

调用链大概是：

1. 请求 A：生成方法 Swagger
2. 请求 B：生成 CreateOrderRequest Schema
3. 请求 C：生成 OrderResponse Schema

✔️ 正好 3 个

⸻

场景 2：复杂接口（真实项目更常见）

createOrder(CreateOrderRequest req) -> Result<OrderResponse>

你实际会变成：

1. 方法 Swagger
2. CreateOrderRequest
3. OrderResponse
4. Result（如果未有 Schema 或需要补全）

👉 这时候就已经是 4～5 个请求 了
而这是“正确的”，不是“浪费”

⸻

五、那这样做会不会太慢？——这是工程优化问题，不是设计问题

你现在问的是**“设计上是不是对的”**，答案是 100% 对。

至于性能：
• 可以并行请求（DTO / Response）
• 可以缓存 Schema 结果
• 可以跳过已有且未变更的实体
• 可以在 Commit 阶段批量合并

这些都是第二阶段优化。

但抽象不能一开始就错。

⸻

六、一个非常重要的补充认知（你已经隐约意识到了）

AI 在你这个插件里，不是“全知的生成器”，
而是“被精确喂上下文的代码补全引擎”。

既然如此：
• 上下文越聚焦 → 输出越稳定
• 任务越单一 → 插入越安全

👉 多请求 ≠ 设计不好
👉 多请求 = 工程可控

⸻

七、我帮你总结一句“可以写进设计文档”的话

你可以直接用这段话：

为保证 Swagger 注解生成的可控性、可插入性与增量更新能力，
插件采用 按代码作用单元拆分的多请求生成策略：
接口方法、入参实体、出参实体分别独立生成与更新，

• 行为：
• 快速触发单接口生成
• 使用默认策略（无复杂交互）

（4）项目树右键 Action
• 支持对象：
• Java 文件
• 目录
• 行为：
• 递归扫描 PSI
• 过滤接口类
• 批量提交生成任务

2.2 代码分析层（Code Analysis Layer）

2.2.1 Controller 识别器

职责
• 判断类是否为 API Controller
• 支持多种注解组合（如 @RestController、@Controller + @ResponseBody）

核心逻辑
• PSI Class 上注解扫描
• 请求映射注解识别（@RequestMapping 等）

2.2.2 接口方法解析器

输入
• PsiMethod

输出
• ApiMethodDescriptor

包含信息
• HTTP Method
• URL Path
• 方法名
• 参数列表（名称、类型、注解）
• 返回值类型
• 已有 Swagger 注解快照

⸻

2.2.3 实体依赖分析器

职责
• 解析接口方法的入参、出参实体
• 构建 Schema 依赖图

实现要点

• 识别集合、泛型、包装类
• 识别枚举与基础类型

2.3 文档生成编排层（Doc Generation Orchestrator）

DocGenerationTask

- targetPsi
- dependencyTasks
- status

⸻

2.3.2 任务拆分策略

规则
• 每个代码作用单元对应一个独立任务
• 不同任务使用不同 Prompt 模板

示例

接口方法
├─ 方法 Swagger 任务
├─ 入参 Schema 任务
└─ 出参 Schema 任务

⸻

2.3.3 任务调度策略
• 方法级任务优先执行
• Schema 任务可并行执行
• 已存在且未变更的 Schema 可跳过

2.4.1 Prompt 结构设计

Prompt 组成
• System Prompt（固定、只读）
• Task Prompt（按任务类型）
• Context Prompt（代码片段）
• Constraint Prompt（约束规则）
• Output Prompt（输出协议）

⸻

2.4.2 Prompt 构建流程

1. 根据任务类型选择 Task Prompt
2. 提取目标 PSI 的最小必要代码
3. 组合约束与输出协议
4. 控制上下文长度

⸻

2.4.3 AI 请求执行

• 支持结果缓存（Schema 级）

⸻

2.4.4 输出校验
• 校验输出是否仅包含合法 Java 注解
• 校验注解是否可编译
• 校验不包含解释性文本
